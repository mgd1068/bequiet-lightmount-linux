Decodierte Interface-2-Kommandos aus dem usbmon3-Capture (OpenRGB Issue #4950,
Anhang "usbmon3 capture.pcapng.gz", https://gitlab.com/CalcProgrammer1/OpenRGB/-/issues/4950).

Herkunft: von einem Dritten (Issue-Ersteller) veröffentlichter, bereits öffentlicher
GitLab-Anhang. Kein eigener Mitschnitt, keine eigenen Tastendrücke. Enthält laut
Melder auch fremden Maus-Traffic (Adresse 3.3.1) — hier bewusst ausgefiltert, nur
Light-Mount-Traffic (Bus 3, Device 2) verwendet.

Filter (Wireshark/tshark, gegen die entpackte pcapng):
  usb.dst=="3.2.4" && usb.src=="host"   -> Kommandos (host -> EP4 OUT, Interface 2)
  usb.src=="3.2.3" && usb.dst=="host"   -> Antworten (EP3 IN -> host, Interface 2)
Payload-Feld: usbhid.data (usbmon-Header ist bereits von tshark geparst, nicht
mehr Teil dieses Felds).

== Bestätigte Header-Struktur (10/10 Kommandos + 10/10 Antworten konsistent) ==

Byte 0-1  (LE u16): Längenfeld. Kommandos: 41,7,7,29,15,15,18,6,29,41.
                     Antworten: immer 6.
Byte 2-3:            konstant 0x0002 in allen 20 Frames.
Byte 4-5  (LE u16): monoton steigender Sequenzzähler über ALLE Kommandos hinweg:
                     0x103e,0x103f,0x1040,0x1041,0x1042,0x1043,0x1044,0x1245,
                     0x1046,0x1047 — Antwort echot exakt denselben Wert.
                     Byte 5 ist normalerweise 0x10 ("Kommandoklasse"?), nur bei
                     frame 2997 ist Byte5=0x12 UND Byte6=0x0a (siehe unten) —
                     zusammen mit dem Sprung auf 0x1245 spricht das für eine
                     andere Kommandoklasse, kein reiner Fehlerfall.
Byte 6:              vermutliche Sub-Kommando-/Typ-ID: 0x06 (7×), 0x02 (2×,
                     kurze Toggle-artige Kommandos), 0x0a (1×, leeres Kommando).
Byte 7:              meist 0x00, bei frame 1739 = 0x01 (direkt nach frame 1731
                     mit Byte7=0x00 — sieht nach einem Flag-Toggle 0→1 aus).
Byte -2..-1 (Ende):  variiert pro Frame, ändert sich mit dem Inhalt — sehr
                     wahrscheinlich eine Prüfsumme/CRC über den Rest des
                     Reports. Noch nicht als konkreter Algorithmus verifiziert.

== Entschlüsselte Nutzlast: Farbverlauf (frame 1453 UND 3531, byteidentisch) ==

Ab Byte 17, in 4er-Gruppen [Position 0-100][R][G][B]:

  Position   0 %  RGB (ff,ff,00)  = Gelb
  Position  17 %  RGB (00,ff,00)  = Grün
  Position  33 %  RGB (00,ff,ff)  = Cyan
  Position  50 %  RGB (00,00,ff)  = Blau
  Position  67 %  RGB (ff,00,ff)  = Magenta
  Position  83 %  RGB (ff,00,00)  = Rot
  Byte 41: 0x64 (100 dezimal) — vermutlich Positions-Byte des 7. (letzten)
           Stopps; zugehörige RGB-Bytes fehlen (Report endet in Nullpadding).

Interpretation (Hypothese, durch zweifache identische, zeitlich getrennte
Übertragung gestützt, aber NICHT durch eigenen Hardwaretest verifiziert):
Dies ist die Definition eines 6-stufigen Regenbogen-/Spektrum-Verlaufs über
den vollen Farbkreis (Gelb→Grün→Cyan→Blau→Magenta→Rot→[Gelb]), passend zu
einem "Rainbow"/"Spectrum"-Hardwareeffekt. Byte 8-16 davor (03 00 64 32 02 07
ff 00 00) sind vermutlich Effekt-ID/Geschwindigkeit/Helligkeit-Parameter,
noch nicht einzeln zugeordnet.

== Offene, nicht entschlüsselte Kommandos ==

- frame 2341/3109 (29 Byte, byteidentisch untereinander): enthält ebenfalls
  Werte 0x64/0x32 (100/50, evtl. Geschwindigkeit/Helligkeit) und einzelne
  Byte-Paare, die NICHT dem [pos][R][G][B]-Schema von oben folgen. Eventuell
  ein anderer Effekttyp (z. B. Breathing mit 2 Farben) — nicht sicher.
- frame 2447/2605 (15 Byte): **Korrektur (2026-08-18, per `report_dump` neu
  geprüft):** es unterscheiden sich ZWEI Payload-Bytes, nicht nur eines —
  Byte 8 (0x01→0x00) UND Byte 9 (0x03→0x00), alle übrigen Payload-Bytes
  identisch (`64 32 00 e6 30 00...`). Sieht nach einem zusammengehörigen
  Feld (z. B. "Kategorie 1 / Auswahl 3" → "Kategorie 0 / Auswahl 0", beide
  Bytes kippen gemeinsam auf 0) statt einem reinen 1-Bit-Toggle aus. Werte
  `e6`(230)/`30`(48) an fester Position in beiden Frames ohne erkennbare
  Prozent-Bedeutung — nicht interpretiert.
- frame 2747 (18 Byte): enthält "01 00 ff 00 ff" — evtl. eine einzelne
  Zweifarb-Konfiguration.
- frame 1731/1739 (7 Byte, Byte6=0x02): kurze Kommandos, vermutlich ein
  Modus-/Tab-Wechsel oder Ein/Aus-Toggle (Byte7 wechselt 0x00→0x01).
- frame 2997 (6 Byte, Byte6=0x0a, Byte5=0x12 statt 0x10): einziges Kommando
  ganz ohne Payload — evtl. eine Abfrage (GET) oder ein "Apply/Commit"-Signal.

== Beobachtung zum Längenfeld (Byte 0-1), noch keine gesicherte Formel ==

frame 2997 (subcmd 0x0a, flags 0x00, Payload komplett leer) hat length=6 — das
ist der kleinste beobachtete Wert und plausibel die "leere" Baseline (6 Byte
Header ohne Payload-Inhalt). frame 1731 (subcmd 0x02, flags 0x00, Payload
ebenfalls komplett leer) hat dagegen length=7, also einen mehr als die leere
Baseline — obwohl auch hier kein Payload-Byte ungleich Null ist. Eine einfache
Formel "length = 6 + Anzahl nicht-Null-Payload-Bytes" erklärt das NICHT (2997
und 1731 hätten dann beide 6). Die Länge scheint also nicht rein aus dem
Payload-Inhalt ableitbar zu sein, sondern hängt (auch) vom Subkommando/der
Kommandoklasse ab — bleibt in `report.h`/`PROTOCOL.md` bewusst als offene
Hypothese markiert, nicht als Formel im Code nachgebildet.

Keine dieser Hypothesen ist bestätigt. Nächster Schritt laut STATE.md: gezielte
Einzelaktions-Captures (eine Änderung pro Aufnahme) statt fremdem Mehrfach-Klick-
Capture, um obige Zuordnungen zu verifizieren oder zu widerlegen.
